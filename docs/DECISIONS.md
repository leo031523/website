# 技術決策紀錄

這份文件記錄專案裡幾個不是「憑直覺」而是有明確取捨考量的決定，格式是「決定了什麼 → 為什麼 → 主要代價」。目的是讓我（或任何審視這份作品的人）事後還能重建當初的判斷依據，而不是只看到最終結果。

## 1. 為什麼用 HttpOnly Cookie 存 JWT，不用 localStorage

**決定**：登入後的 JWT 放在 `HttpOnly` + `SameSite=Lax`（正式環境再加 `Secure`）的 cookie 裡，前端 JavaScript 完全讀不到這個 token。

**為什麼**：localStorage 對任何能在頁面上執行的 JavaScript 都是完全開放的，只要出現一個 XSS 漏洞（例如 Markdown 渲染沒擋乾淨、或第三方套件被下毒），攻擊者就能直接把 token 讀走。HttpOnly cookie 讓「讀取 token」這件事從「任何一段 JS 都做得到」降低成「要能執行任意 JS 且繞過瀏覽器本身的 HttpOnly 保護」，防禦層次不一樣。

**代價**：CSRF 風險回來了——瀏覽器會自動幫你把 cookie 帶上，所以要另外處理跨站偽造請求。我們的處理方式見下一條。

## 2. 為什麼沒有另外做 CSRF token，只靠 SameSite + CORS

**決定**：Cookie 設 `SameSite=Lax`，後端 CORS 只允許明確列出的來源（`CORS_ORIGINS`），沒有實作額外的 CSRF token 機制。

**為什麼**：`SameSite=Lax` 讓跨站的「非導覽型」請求（例如另一個網站用 JS 發出的 POST/PUT/DELETE）預設不會帶上這顆 cookie；就算攻擊者想繞過，跨站的 fetch/XHR 請求會先觸發 CORS preflight，而我們的 allow-list 只認自己的網域，瀏覽器會直接擋在 preflight 階段，請求根本不會送達後端。兩層疊加後，CSRF token 帶來的邊際防禦很小，卻要多維護一組「產生、夾帶、驗證」的邏輯與對應測試。

**代價**：這個判斷仰賴「瀏覽器正確實作 SameSite 與 CORS」這個前提；如果之後要支援舊瀏覽器或需要跨網域嵌入，就要重新評估。

## 3. API key 為什麼要加密，不能只在後台做遮罩顯示

**決定**：AI provider 的 API key 用 Fernet 對稱加密後存進資料庫（`encrypted_api_key`），加密金鑰（`AI_MASTER_KEY`）另外用環境變數注入；後台讀取設定時只回傳遮罩後的尾碼（例如 `****ab12`），前端從來拿不到明文，也絕不接受把明文塞進 log。

**為什麼**：「遮罩顯示」只解決了 UI 層面「不要讓人一眼看到完整 key」的問題，但如果資料庫本身外洩（備份檔外流、SQL injection、內部人員誤操作），明文儲存的 key 會直接被拿走。加密儲存把防線往前推一層：就算資料庫外洩，沒有 `AI_MASTER_KEY` 的攻擊者拿到的只是密文。

**代價**：`AI_MASTER_KEY` 本身變成單點故障——遺失就等於遺失所有已存的 API key，只能請管理者重新輸入一次。這是刻意接受的取捨：比起「用一把固定或簡單可猜的 key」換取「永遠不會遺失」，寧可要求正式環境必須設定夠長的隨機 master key（少於 32 字元或用預設值會直接拒絕啟動）。

## 4. 自訂 Base URL 為什麼可能造成 SSRF，怎麼防

**決定**：Gemini、OpenAI、Claude 一律使用程式內寫死的官方 endpoint，使用者輸入完全不會變成實際請求的目標；只有「OpenAI 相容服務」允許自訂 Base URL，而且正式環境預設拒絕這個 URL 解析出的 IP 落在 loopback、內網、link-local（含雲端 metadata IP `169.254.169.254`）範圍，或 scheme 不是 http(s)。

**為什麼**：如果後端願意「原樣照著使用者填的網址發送請求」，而後端伺服器本身通常部署在有內網存取權限的環境（雲端 VPC、能連到 metadata service），這就是教科書等級的 SSRF：攻擊者把 Base URL 填成 `http://169.254.169.254/latest/meta-data/iam/...` 就可能撈到雲端服務帳號的憑證。因為 DNS 也可能被用來繞過純字串比對（先讓網域看起來正常，實際解析到內網 IP），檢查是對「解析後的 IP」做，不是對網域字串做。

**代價**：本機開發如果要接自架模型（例如 Ollama）沒有這層限制（`APP_ENV` 不是 `production` 時不擋），但正式環境如果真的要連內網模型，必須把主機名稱明確加進 `AI_LOCAL_MODEL_ALLOWLIST`，不能圖方便直接關掉檢查。

## 5. 怎麼避免 AI 產生不存在的來源（citation 幻覺）

**決定**：System prompt 要求模型引用時必須用我們提供的 `[來源: xxx]` 格式；但後端從來不信任模型輸出的引用內容本身——收到回答後用 regex 抓出所有 `[來源: xxx]` 標記，只保留那些 ID 剛好等於「這次檢索結果」裡真的存在的 chunk id，其餘一律捨棄。標題、URL、摘要永遠是後端根據真正的 chunk 資料重新產生，不是從模型輸出裡剖析出來的。如果一個回答最後沒有任何有效引用（不管是模型没引用，還是引用的 ID 全部是幻覺），就整個降級成固定的拒答文字，不會把「聽起來合理但沒有依據」的內容原封不動地展示給使用者。

**為什麼**：語言模型本質上會「編」——它可以生成一個看起來完全合理的 URL 或標題，但那個東西未必存在。信任模型自己聲稱的來源等於把「事實查核」的責任外包給一個沒有事實查核能力的東西。

**代價**：這個機制天生保守——模型如果生成了正確的答案卻忘記加引用標記，也會被降級成拒答。這是刻意的取捨：寧可漏掉一些「其實答對了但沒附來源」的回答，也不要讓「沒有來源支撐」的內容被當成可信答案端出去。

## 6. 關鍵字檢索與向量搜尋（vector search）差在哪裡，為什麼先用前者

**決定**：MVP 用關鍵字比對（含 CJK bigram 分詞，緩解中文單字誤配的問題），把長文章切成有重疊區段的 chunk，設定最低相關度門檻與單一來源最大 chunk 數，沒有內容通過門檻就不呼叫模型、直接拒答。沒有導入 embedding model 或向量資料庫。

**為什麼**：向量搜尋比對的是「語意相近」，關鍵字比對比對的是「字面出現過」——前者理論上能處理「使用者問法跟文章寫法不同但意思一樣」的情境，但也需要額外維護 embedding pipeline（發布/更新/下架都要同步 re-index）、選定 embedding model、處理 model 換版後舊 embedding 失效的問題。以這個網站目前的內容量（十幾篇文章等級），關鍵字檢索的召回率已經夠用，換向量搜尋的邊際效益抵不過額外的維運複雜度。

**代價**：使用者如果用完全不同的措辭問問題（例如問「這個網站有沒有防止機器人亂猜密碼」但文章寫的是「rate limiting」），關鍵字比對可能找不到對應內容而直接拒答。這是已知、可接受的限制，寫在使用者看得到的說明裡（不宣稱是語意搜尋），而不是假裝系統比實際更聰明。

## 7. Provider timeout、429 與費用失控怎麼處理

**決定**：每次呼叫 provider 都帶明確的 timeout（可設定，預設 30 秒）；timeout、429、5xx 用有限次數（2 次）的 exponential backoff 重試，401/403/400 這種「重試也不會變好」的錯誤不重試、直接回傳分類後的錯誤；限制單次最大輸出 token 數；公開聊天 API 有 IP 層級的每分鐘與每日請求上限（in-process 計數，個人網站規模不需要另外引入 Redis）；第一版不會在一個 provider 失敗時自動切換到另一個付費 provider。

**為什麼**：AI API 是按用量計費的外部服務，沒有節流機制的話，一次爬蟲攻擊或使用者意外的重複點擊都可能造成不可預期的帳單。自動切換 provider 聽起來貼心，但等於讓系統在你不知情的情況下決定要花另一家的錢，屬於「這個階段不納入」的範圍。

**代價**：使用者在 provider 真的掛掉時只會看到「暫時無法使用」，不會自動改用備援方案；這需要管理者自己發現並手動處理。

## 8. 如何驗證 AI 產生的程式與回答

**決定**：每個「AI 助理」的行為（RAG 檢索、citation 驗證、prompt injection 防禦、錯誤分類）都有對應的自動化測試，而不是「畫面看起來會動」就算過；關鍵行為額外用「刻意讓測試失敗」的方式驗證測試本身有效（例如故意還原某個安全修復、確認測試真的會抓到，再改回來）。功能性的部分（尤其是 UI 互動、瀏覽器行為）在真實或等價於 CI 的環境裡手動跑過一次，包含真的用瀏覽器操作、真的用一次性測試帳號跑過完整流程、再把測試資料清乾淨。

**為什麼**：AI 生成的程式碼容易出現「看起來對、但有微妙的假設是錯的」的情況（例如這個專案實際發生過：焦點陷阱邏輯選到一個 disabled 的按鈕、Playwright 的 URL 拼接因為前導斜線把 base path 吃掉、CORS 缺少 preflight 處理）。這些問題都不是「看程式碼」就能發現的，是實際跑過、實際測過才抓到的。

**代價**：這個流程比單純「叫 AI 寫完就收工」慢很多，但這正是這個專案想展示的能力——AI 協作的價值在於加速迭代，不是取代驗證。

## 9. 測試資料庫怎麼隔離，CI 怎麼跑 migration

**決定**：後端測試用獨立的 Postgres（本機是另一個 docker service，CI 是 GitHub Actions 的一次性 service container），每個測試案例用隨機字串產生自己的帳號/資料，測試結束後透過 fixture 自動清除，測試之間不共用狀態、也不依賴執行順序。CI 每次都是全新資料庫，先跑 `alembic upgrade head` 確認 migration 能在空資料庫上完整套用，才開始跑測試；E2E 也是同樣的全新資料庫 + 全新後端，跑完即丟。

**為什麼**：如果測試共用同一個資料庫或依賴彼此的資料，測試結果會受執行順序影響，「在我電腦上過」但 CI 上不過（或反過來）的情況會變得很難排查。全新資料庫 + migration from scratch 也順便驗證了「這個專案真的能在一個空環境從零建立」，不是只能在開發者自己那台已經手動修過的資料庫上運作。

**代價**：每個 CI job 都要重新跑一次 migration 與環境建置，比共用一個長駐測試資料庫慢，但換來的是結果可信賴、可重現。

## 10. 正式網站出錯時，怎麼透過 log 與 request ID 定位問題

**決定**：每個請求都會產生一個 `request_id`（透過 middleware，回應標頭帶 `X-Request-ID`），結構化 JSON log 記錄 method、route、status、耗時；發生例外時額外記錄錯誤類型。AI 聊天 API 的公開錯誤只回傳安全的錯誤分類與 `request_id`，詳細原因（provider 回傳了什麼、是哪個 provider、失敗分類）只寫在後端 log。Log 內容經過設計，不含密碼、JWT、API key 或請求/回應本文。

**為什麼**：使用者回報「AI 助理壞了」時，如果錯誤訊息只有「發生錯誤」四個字，開發者要重現問題非常困難；但如果錯誤訊息直接把 provider 的原始錯誤或 stack trace 丟給使用者，又可能洩漏內部細節。`request_id` 讓「使用者看到的東西」跟「開發者需要除錯的細節」脫鉤——使用者看到的永遠是安全、穩定的訊息，開發者可以拿同一個 ID 去 log 裡查到完整脈絡。

**代價**：這個機制的價值建立在「log 真的有被保存、有被查看」的前提上；目前 log 只寫到 stdout（由 Docker 收集），沒有另外接到集中式的 log 平台，正式環境長期營運的話這會是下一個要補的環節。
